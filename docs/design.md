# 自動化ラン制ゲーム 設計書 v0.2.5


- 検証指標を全面差し替え

## 変更履歴
- v0.2.1: 状態判定規則の明文化、搬送スロットの強化対象外を明記

## 1. コンセプト

- 1ラン12分（暫定）で「時間内にどれだけ稼げるか」を競う自動化ゲーム。
- レイアウト作業なし。悩みの中心は投資判断とボトルネック解消。
- アニメーションは情報伝達の一次手段。詰まりは数字より先に絵で分かる。

## 2. 設計目標（受け入れ条件）

「理論上の最適解をなくす」は目標にしない。以下を満たすことを目標とする。

- G-1: どの周回補正でも同一の固定戦略が首位にならない
- G-2: 新設・強化・貯金それぞれが最適になるゲーム状態が存在する
- G-3: 残り時間・バッファ状態・台数によって投資順位が実際に逆転する
- G-4: 上位2戦略のスコア差が極端にならない
- G-5: 連続無操作時間が15〜20秒を超えない

## 3. ゲーム構造

### 3.1 生産ラインと状態モデル

[採取器群] → bufferA → [加工器群] → bufferB → [出荷口]

- 状態変数: 所持金, スコア, bufferA量, bufferB量, 各工程の台数/強化Lv
- 更新は固定時間刻み（仮: 100ms/tick）。描画フレームに依存させない
- 各tick:
  - 採取器は bufferA に空きがある分だけ生産（満杯なら停止=blocked）
  - 加工器は bufferA から取り出せる分だけ処理（空なら starved）、
    bufferB に空きがある分だけ出力（満杯なら blocked）
  - 出荷口は bufferB から取り出せる分だけ出荷し、単価×個数を収入化
- バッファ容量は有限（仮: 各20。simulatorで掃引して決定）
- min()式は設計説明用の定常近似としてのみ使用。実計算はバッファ入出力
- ラン終了時の残バッファはスコアに換算しない

### 状態判定規則
- 各工程の状態は完全停止のみを starved / blocked とする。
  部分充足（空き容量や在庫が需要より少ないが0ではない）は running 扱い。
- 「詰まりかけ」の表現は状態ではなくバッファ充填率（A-2）が担う。
- game-core は各工程の utilization（実効処理量 ÷ 需要量、0〜1）を
  state に保持し、renderer / simulator が補助指標として参照できる。


### 3.2 系統（工程単位）

- 系統は3種（題材はTBD-1。仮: 金属/樹脂/ガラス）
- 系統は装置単位ではなく**工程単位**。採取・加工・出荷の各工程に1系統を設定
- 同一工程内の装置は同系統に限定。多数決・主力判定は使わない
- 工程の系統はラン中に変更可能か → TBD-2（初期案: 変更不可。ラン開始時に3工程分を選択）

### 3.3 投資

投資対象は5スロット: 採取 / bufferA(搬送) / 加工 / bufferB(搬送) / 出荷

| 選択 | 効果 | 性格 |
|---|---|---|
| 新設 | 装置工程: 台数+1 / 搬送: 容量+α | 即効・線形 |
| 強化 | 1台あたり処理量+10%（仮）。効果はN秒かけて線形に立ち上がる | 遅効・非線形 |
| 高額装置 | 1種のみ（3.5）。貯金して狙う転換点 | 跳躍 |

- 強化の対象は装置3工程（採取・加工・出荷）のみ。
  搬送（bufferA/B）への投資は新設（容量+α）のみとする。

- 強化立ち上がりN: 60秒と120秒の2案をプロトタイプで比較（30秒は12分ランでも弱い）
- コスト式: 新設 = base × 1.15^n（仮）。強化価格は台数連動を含めて設計する
  （新設価格だけが指数上昇すると後半は強化固定解になるため）
- 価格・効果はラン開始時から全開示

### 3.4 シナジー（効果軸分離）

- 統一（3工程が同系統）: 投資効率系。新設費用-20% かつ 強化立ち上がり半減（仮）
- 混成（3工程が全て異系統）: 収入系。出荷単価+40%（仮）
- 最終収益倍率同士の直接比較を不能にすることが目的。
  拮抗はsimulatorで検証し、どちらかの採用率が70%を超えたら数値を調整する
- 倍率上限規則（合計×1.5以内・乗算重ね掛け禁止）はシナジー同士に適用する。
  シナジー×周回補正の複合（例: mixed×compactBuffers）は上限の対象外とするが、
  複合ケースのバランスは検証指標（§6）で必ず確認する。
- 特定ペアはv0.2スコープ外（保留リスト）

### 3.5 高額装置（1種のみ）

- 要件: 購入後に投資の価値順位が変わる「転換点」であること
- 仮案「二次加工器」: bufferBの製品をさらに高級品化して単価×4
  （第2回バランス改訂で ×3 → ×4。config: `secondaryProcessorPriceMultiplier`）。
  ただし専用の処理能力を持ち、新たなボトルネック段として追加される
  → 購入前は採取/加工強化が正解だった盤面が、購入後は二次加工と出荷の
    増強が正解に変わる

#### 受け入れ条件（積立予約の時刻依存で測る）

「転換点であること」を定性的な説明で終わらせず、
**予約時刻 → 最終スコアの差分（デルタ）曲線**で判定する。
デルタ = その時刻に予約したランのスコア − 予約しなかったランのスコア。

1. デルタ曲線に**負の領域が存在する**こと（早すぎる予約は損になる）
2. **最適な予約時刻がラン長の 20〜40%** に位置すること
3. デルタが**ピークの 50% 以上を保つ時刻幅が、ラン長の 30〜60%** に収まること
   （狭すぎると当てもの、広すぎると常に正解になり判断が消える）
- 効果の具体はTBD-3。ただし「単なる大倍率」は禁止
- 二次加工器は精錬品バッファ（容量 仮:10。configで調整可）を持つ。
  満杯時は精錬を停止する（bufferBからの取り出しも行わない）。
- 精錬品バッファは有限バッファ原則（§3.1）に従い、rendererから
  充填率を参照できること。
- 出荷は精錬品を通常品より優先する（単価が高いため。プレイヤー選択なし）。
- ラン終了時の精錬品残はスコアに換算しない（§3.7と同じ扱い）。
- 二次加工器は購入後、statuses.secondary として状態を返す:
  - running: 精錬を実行した
  - starved: bufferB が空で精錬できない
  - blocked: 精錬品バッファが満杯で停止している
  - 未購入・予約中は null（表示対象外）
  - ramping は存在しない(二次加工器に強化はないため)

### 積立予約
- 二次加工器は即時購入ではなく「予約」で取得する。
- 予約時に天引き率を選択する（収入の25% / 50%。config値）。
  以後の出荷収入から天引きされ積立される。積立中も残りの所持金で
  通常投資が可能。
- 積立が価格に到達した時点で自動的に購入・稼働開始する。
- 予約はいつでも解除でき、積立額は全額所持金に戻る。
  貯金の失敗は引き続き機会損失として表現される（没収はしない）。
- 天引き率はラン中に変更可能とするか → 実装時に固定で開始し、
  バランス検証後に判断（TBD）。

  

### 3.6 周回補正（3種・関係変更型）

- 補正は「特定系統の大幅割引」のような答えの指定を禁止し、
  投資間の関係を変えるものに限定する。仮案:
  - 強化の立ち上がり時間 1/2
  - バッファ容量-30%、代わりに出荷単価+30%
  - 新設価格上昇率 1.15 → 1.10
- ラン開始時に1つ抽選
- compactBuffersの容量倍率は初期容量にのみ適用する。
  ラン中の増設（bufferA/B新設 +α）は等倍とする。
  （補正ラン中は増設の相対価値が上がる。これは意図した挙動）

### 3.7 スコアとラン終了

- スコア = 出荷による累計収入。投資してもスコアは減らない
- 所持金 = 投資用残高（スコアとは別管理）
- 終了時所持金はスコアに加算しない
- 貯金の失敗 = 貯金中に見送った投資の機会損失として自然に表現される

### 3.1 観測値（表示専用・スコアに不関与）

- `utilization`: 各工程の稼働率（実効処理量 ÷ 需要量, 0〜1）
- `throughput`: 各工程の直近tickの実効処理量（個/秒）。二次加工器も含む。
  tick内で既に算出している量を公開するだけで、計算ロジックには関与しない
- いずれも在庫（`buffers`）とは独立した量である

## 4. アニメーション要件

受け入れ条件: 数値表示を読まずに以下が分かること。

- A-1: 資源が粒として流れる
  - 粒は表示専用。game-coreの公開状態から生成（1粒=N個の代表表示）
  - 粒オブジェクト再利用、最大表示粒数を設定
  - **2つの根拠を役割分担させる**
    - 粒の「数・流れる速さ」… 実効処理量（流量, 個/秒）由来
    - 粒の「密集・滞留・停止」… バッファ在庫量由来
  - この2軸は独立している。在庫0でも流量があれば粒は流れ、
    流量0でも在庫があれば粒は溜まって止まる。
    在庫のみを根拠にすると、健全状態（在庫0・全工程running）で搬送路が空に描かれる
  - 流量は game-core が観測値として公開する（§3.1 の `throughput`, 個/秒）。
    描画側でレート計算式を再実装しない
- A-2: 詰まりが渋滞として見える（最重要・最難）
  - 滞留の表示は**バッファ充填率0〜100%**から変換する（流量ではなく在庫が根拠）
    - 0〜50%: 滞留分の粒数が増える
    - 50%〜: 粒間隔が狭くなる
    - 流量由来の粒数と在庫由来の粒数は、多い方を採用する
  - 詰まり表現（搬送路の圧縮/点滅）の発動条件は**容量に依存しない量**とする。
    充填率の固定閾値（旧: 90%）は、投資でバッファ容量が伸びた局面（容量114/164など）で
    実際に詰まっていても発動しないため採らない
    - 判定は「滞留量が継続して増加している時間」。増加が一定秒数続いたら発動し、
      さらに継続すると表現が強まる。滞留が減り始めれば解除する
    - 判定に使う値は game-core の公開状態（バッファ量・statuses・utilization）のみ。
      描画側でゲーム計算式を再実装しない
  - 上流装置の停止（充填率100% または status=blocked）は、静的表現で明確に見える
- A-3: 装置状態のモーション切替
  - game-coreが状態を返す: running / starved / blocked / ramping
  - 描画側で状態を推測しない。表示切替に最低継続時間200〜500ms
  - 稼働の度合いは `utilization`（0〜1）を**連続量**として可動部の速度・粒の流量へ写像する。
    二値（動く/動かない）にしない
  - ただし**完全停止（starved / blocked）は連続量と区別できる離散表現**とする。
    低稼働（遅く動いている）と停止が混同されると詰まりの発見が遅れるため、
    速度0に加えて静止画でも判別できるバッジ等を重ねる（点滅のみに依存しない）
- A-6: 律速段の明示（視覚言語で行う。文字ラベルを置かない）
  - 全装置に**共通の稼働メーター**を置き、`utilization` を目盛りとして示す。
    メーターは装置本体に埋め込み、装置から視線を外さずに読める位置・大きさにする
    律速段は「メーターの振り切れ」として相対的に読ませる。
    どの装置が律速かを名指しする文字ラベル（「律速」等）は置かない
  - 振り切れは色だけでなく形の差分（針が右端を超える表現）で示し、
    色覚に依存させない
  - 示すのは**「どこが詰まっているか」まで**。対処方法（新設 / 強化 / 貯金）は示さない。
    対処の選択は本作の中心的な悩み（§6 G-2/G-3）であり、推奨手を提示すると
    表示された段を買うだけの作業に退化する
  - 禁止: 推奨アクション文言、律速段の投資項目の強調・並べ替え・色分け、
    解決コスト（「あと◯円」）の提示
- A-7: 説明を文字に頼らない
  - 説明はアイコン・バッジ・計器で行い、画面に常設するテキストを増やさない
  - **装置本体は無彩色に統一し、色は状態表現（稼働 / 抑制 / 停止 / 振り切れ）にのみ割り当てる**。
    系統（金属 / 樹脂 / ガラス）は粒と可動部のアクセントで示し、状態色と競合させない
  - `starved` / `blocked` は粒の語彙で表す
    - starved: 入力側に**空の受け皿**（粒がゼロであること自体を見せる）
    - blocked: 出力側に**溢れる粒**（受け皿から粒がこぼれる）
    - 既存の色（灰 / 赤）は補助として維持し、形の差を必ず併せ持つ
  - 画面に内部名（bufferA / bufferB 等）を出さない。搬送路は工程間の位置で示す
    （例: 「採取 ▸▸ 加工」）。投資項目も同様に工程列の位置が分かる表記にする
  - 補足テキストはマウスオーバー時のみ表示する（常設しない）
  - **低稼働の理由**は**装置の辺**で示す。完全停止していなくても（部分的な抑制でも）
    読み取れること。小さな図形は通しプレイで視認できなかったため、輪郭を語彙にする
    - 材料待ち（上流不足）: 入力側（左辺）が破線状に欠ける＋内向きの爪
    - 出口待ち（下流飽和）: 出力側（右辺）が連続した帯で詰まる＋外向きの爪
    - 辺の太さと濃さで度合いを示す
    - 濃さは抑制の度合い（1 − `utilization`）に比例させる。完全停止時は
      停止の語彙（等倍の受け皿・溢れる粒＋停止バッジ）に切り替え、二重に出さない
    - 判定は公開状態のみから行う。採取の入力（採取源）と出荷の出力（工場外）は
      無限であり、その側は理由になりえない
  - 二次加工器は、精錬品の在庫が0でも精錬中であることが本体の変換モーションで分かること
    （在庫0＝停止に見える問題への対処）
- A-4: 購入と効果発生の演出分離
  - 購入時: 設置演出。ramping中: 充填ゲージ。完全効果到達: 完了演出
- A-5: 出荷演出の時間集約（M2で実装）
  - 出荷粒が出荷口を抜けて工場外へ出る。粒の生成は流量（`throughput.shipping`）由来
  - 収入表示は同時に1つだけとし、出荷が連続しても重ならないこと
  - 100〜500ms単位で出荷をまとめ「+125 / 12個出荷」形式で表示
  - 個別粒の出荷表現と金額表示の更新頻度を分離

マイルストーン1の対象はA-1〜A-3の最小表現。A-4は後続。
A-5はM2（可読性とUX）で実装した（収入が発生したことが見えないため）。

### 状態モーション対応
- running: 可動部アニメ（ドラム回転/プレス上下動/ベルト流動）
- starved: 可動部停止＋入力側を淡色点滅
- blocked: 可動部停止＋出力側を赤系点滅
- ramping: 装置上に充填ゲージ表示

### 受け入れ条件の客観化（「詰まり箇所を指差せる」の判定基準）
以下を数値なし表示（デバッグ数値を隠した状態）で満たすこと:
1. いずれかのバッファで滞留の増加が継続しているとき、該当搬送路の圧縮/点滅表現が
   他の搬送路と明確に区別できる。バッファ容量を投資で拡張した後（容量114/164相当）も
   同条件で発動する
2. blocked/starved の装置が、runningの装置と静止画でも区別できる
   （点滅に依存しない色または形の差分があること）。低稼働で動いている装置とも区別できる
3. 粒の流量変化（装置追加前後・稼働率の変化）が搬送路の見た目に反映される。
   在庫0でも流量があれば粒が流れて見える
4. 律速段がどこかを指差せる。かつ画面上に対処方法（新設 / 強化 / 貯金）を
   示す表現がない
5. 文字を読まずに「どこが上限か」「なぜ止まっているか」が判別できる
   （稼働メーターの振り切れ / 空の受け皿 / 溢れる粒）
6. 文字を読まずに「なぜその工程が抑えられているか」（材料待ち / 出口待ち）が
   判別できる。完全停止していない部分的な抑制でも判別できること
7. 出荷された製品が工場外へ出ることと、収入が発生したことが見える。
   出荷が連続しても収入表示が重ならない
8. 装置の色から状態が判別でき、系統色と状態色が混同しない
9. 滞留が容量に近づいたことが、数値を読まなくても分かる

## §4-V ビジュアル方針（MS3）

### V-1. 色の四重防御

情報設計（状態が読めること）を装飾で侵さないため、4つの独立した軸で分離する。

| 軸 | 装飾 | 状態 | 素材（粒） |
|---|---|---|---|
| 彩度 S | ≤ 10% | ≥ 55% | 30〜70% |
| 輝度 L | ≤ 0.42 | ≥ 0.60 | 0.50〜0.72（精錬品のみ ≥ 0.78） |
| 色相 H | — | 0〜40°（橙赤）/ 140°（緑） | 190〜265° に限定 |
| 合成モード | source-over | lighter（加算） | source-over |

- 状態色: 稼働 `#57E28C` / 材料待ち `#E9EEF3` / 出口詰まり `#F0554F` / 立ち上がり `#F5A340`
- 材料待ちの白は S≈29% で彩度ルールを満たさないため、**輝度 L ≥ 0.90 で分離**する
- 素材色: 金属 `#8FA8C4`（角）/ 樹脂 `#9B7FE6`（丸）/ ガラス `#4FBCD6`（三角・α0.75）
  形でも判別できるようにし、色だけに依存しない
  ※ 現行の樹脂の橙 `#e07a3f` は「立ち上がり中」の橙と衝突するため置換する
- 精錬品 `#ADE0EB` は系統（金属/樹脂/ガラス）と直交する「加工段階」の軸なので、
  色相を素材帯（190〜265°）に置いたまま**輝度 L ≥ 0.78 で階層を付ける**。
  形は菱形＋発光縁。金色 `#d9a441` は立ち上がりの橙と色相10°差で衝突するため使わない
- 素材の彩度に上限を置かない理由: 素材と状態を分けているのは色相であり、
  素材帯に入る状態色は材料待ちの白（H210 S29% L0.93）だけで、彩度と輝度で分離済み
- 装飾パレット例: 奥壁 `#16181A`→`#1E2124` / 床 `#202327`→`#2A2D32` /
  装置上面 `#4E545B` / 正面 `#3D4249` / エッジライト `#646A72` / エッジシャドウ `#151719`
- 白黒αの重ね（ハイライト・影）は「登録する色」ではなく合成結果なので検査対象外。
  ただし**白は α ≤ 0.12、黒は α ≤ 0.50** を上限とする。
  これを超えると合成後の輝度が状態色の領域に食い込む

### V-2. 面積と位置による担保

状態色を塗ってよい領域を限定する。装置本体の大面積を状態色で塗らない。

- 許可: 状態ランプ / 筐体下部の稼働バー / 外周1〜2px / 装置の辺（入力側・出力側）
- 禁止: 筐体全体の着色、内部ユニットの個別着色

### V-3. ルールの担保方法（人力で守らない）

1. `PALETTE.decor` / `PALETTE.state` / `PALETTE.material` の3オブジェクトに分離
2. 描画コードに色リテラルを直書きしない
3. 起動時に各色をHSLへ変換し、上記の範囲を検査。外れたら `console.error`

### V-4. 質感の技法（Canvas 2D）

- 金属は輝度の急な折り返しで表現する。縦グラデのストップを不等間隔にし、
  明るい帯の幅を 0.04 程度に抑える（広げるとプラスチックに見える）
- エッジは上端1px明色・下端1px暗色を `fillRect` で置く（`strokeRect` は0.5pxずれてボケる）
- 角丸半径は 4〜6px（10px以上はUIカードに見える）
- 重量感は接地影で出す。横長楕円の放射グラデ＋本体形状のオフセット影（dx=3, dy=5）
- ノイズ・ヘアラインは焼き込み時のみ（`overlay` α0.04、傷は角度を -12〜-18° に揃える）
- 光源は真上やや左（-15°）に固定。装置ごとに影の向きを変えない
- 搬送レーンは一本線ではなく多層構造にする
  （下部フレーム / ベルト面 / 下側影 / ローラー継ぎ目 / 上辺ハイライト1px）

### V-5. 構図

- **横一列を維持する。** 工程の因果（左が詰まると右が飢える）と視線移動の方向が
  一致しており、崩すと詰まり箇所の探索が発生する
- 装置の接地線をキャンバス高の 42〜52% に置き、下部を床と手前の設備に使う
- 3層構成: 奥壁（縦グラデ）/ 中景シルエット（輝度差3以内・静止）/ 床（縦グラデ）
- 床グリッドは手前ほど間隔を等比 1.18 倍で広げる（透視変換なしに奥行きが出る）
- ビネット（四隅・黒 α0.35）は静的に焼く
- 柱と梁を背景に置く。装置の大きさを比較する基準として機能させる
- 配置ピッチは固定し、成長しても装置列の左右端を動かさない

### V-6. 成長段階（設備バンク方式）

1台＝1オブジェクトで並べない。台数を「バンク（設備群）」に集約する。

- 1バンク = 最大10室。**バンク上限は3基（30室）**
- 実測では1工程あたり最終16〜21台のため、2バンク前後で収まる
- 各室は単なるドットにせず、小型処理室＋可動部＋1pxハイライトを持たせ、
  室ごとに動作位相をずらす
- 状態はバンク全体で表示し、内部の室を状態色で塗らない
- 搬送レーンの多重化は最大3本。以降は粒の密度と流速で表現し、描画数を増やさない
- 粒の同時描画数は最大120個で固定

### V-7. 性能の原則

- 装置の静的部分（本体・グラデ・ボルト・ノイズ・傷）はオフスクリーンに1回焼き、
  毎フレームは `drawImage` 1回にする。これが本体で他は誤差
- `ctx.shadowBlur` を毎フレーム使わない。影はグラデーションか焼き込みで
- グラデーションをフレームループ内で生成しない
- 粒は色ごとにバッチし、`beginPath()` 1回・`fill()` 1回で描く
- 合成モードの全面適用は焼き込み時のみ
- `devicePixelRatio` は最大 1.5〜2.0 に制限
- Canvas 3層構成（背景 / 設備 / 動的エフェクト）

### V-8. 禁止事項

1. 装置本体に金属の青みや錆の茶色を入れる（状態色と混同される）
2. 筐体全体を状態色で塗る（大面積の着色は画面が警告表示に見える）
3. 装飾に発光・グローを使う（高彩度・高輝度は状態表現の予約枠）
4. 台数を1台＝1オブジェクトで並べる（20台でレイアウトが破綻する）
5. 成長を単純な拡大率で表現する（他工程を圧迫する。外形に上限を設ける）
6. 台数を示す数値ラベル（"Lv.20" "×50" 等）を装置上に描く
7. 常時動く蒸気・火花・照明点滅を大量に追加する（粒＝情報と競合する）
8. 購入可能な装置を光らせる・脈動させる（投資の誘導に当たる）
9. 装置ごとに光源方向を変える
10. 背景に高コントラストの格子や警戒線を置く

## 5. 技術方針

- HTML + Vanilla JS + Canvas
- 構成分離:
  - game-core.js: 固定時間刻みの状態更新。全定数・全計算式の唯一の正
  - renderer: requestAnimationFrameで描画。game-core状態の純粋な投影
  - simulator.js: game-coreのみを高速実行
  - particles: バッファ量・流量から生成する純表示（ゲーム計算に不関与）
- 収益・進行を描画フレーム数に依存させない
- セーブ: ランセーブとメタ進行を別キーでlocalStorage保存
- 体制: Codex=実装（範囲限定・設計判断禁止）、Claude=設計・レビュー、人間=採用判断
- game-core.js は CommonJS + ブラウザグローバル（window.GameCore）の
  デュアルエクスポートとする。ビルドツールは導入しない。

## 6. 検証指標（simulator.js）

- 補正別に各戦略の平均・中央値・下位分位スコア
- 同一固定戦略が全補正で首位になる割合（G-1）
- 新設/強化/貯金それぞれが最適になる状態の存在確認（G-2, G-3）
- 上位2戦略のスコア差（G-4）
- 有効な購入判断の発生間隔、連続無操作時間（G-5）
- 高額装置購入前後での投資優先順位の変化（3.5の転換点検証）
- バッファ容量の掃引（小さすぎ=頻繁停止 / 大きすぎ=在庫戦略復活 の境界確認）
